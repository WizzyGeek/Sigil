```
CLIENT      React + TypeScript + Vite + Tailwind CSS
REGISTRY    Python + FastAPI + PostgreSQL

```

## CLIENT

### Core Stack
```
Framework:      React 18+
Language:       TypeScript (strict mode)
Build tool:     Vite
Styling:        Tailwind CSS
```

### Key Libraries
```
JWT handling:   Custom implementation using Web Crypto API (no external JWT lib)
                Reason: external JWT libs require private key access.
                Web Crypto keeps private key in IndexedDB, unexported.
                Build JWT manually: base64url(header) + "." + base64url(payload)
                then crypto.subtle.sign() for the signature.

Crypto:         Web Crypto API (built into all modern browsers, no install needed)
                Algorithms used: RSASSA-PKCS1-v1_5 with SHA-256 (RS256 equivalent)

Key storage:    IndexedDB (via idb library for cleaner async API)
                Private key stored as non-extractable CryptoKey object.
                Private key bytes NEVER appear in application code. Ever.
                Public key exported as PEM for submission to Registry.

WebSocket:      Native browser WebSocket API (no library needed)
                Or EventSource for SSE fallback.

HTTP client:    fetch() native API (no library needed)
```

### UI Design Specification
```
Theme:          Dark / black background
Style:          Glassmorphism
                Cards: semi-transparent with backdrop-filter blur
                Borders: subtle white/grey with low opacity
                
Note Cards:     Pinterest-style masonry grid layout
                Cards appear as they arrive in real time
                
Card Layout:
  TOP RIGHT:    Freshness score — lock icons (🔒 × 0–5)
  BOLD WHITE:   Display name
  BELOW NAME:   @handle@registry.example.com (muted, smaller)
  CARD BODY:    Note content
  CARD FOOTER:  Timestamp, channel name, reply indicator if applicable

Bottom Bar:     Fixed text input field for composing and sending notes
                Channel selector alongside text input
                Send button triggers: stake fetch → UNT construction → broker push
```

### Key Management UI Flow
```
FIRST VISIT:
  1. App detects no keypair in IndexedDB
  2. Prompt: "Generate new identity" or "Import existing keypair"
  3. On generate: crypto.subtle.generateKey() → store in IndexedDB
  4. Show public key fingerprint to user as their identity
  5. Prompt to register with Registry (user_tag, display_name, email for recovery)

RETURNING VISIT:
  1. App loads keypair from IndexedDB silently
  2. No password needed (key is stored by browser)
  3. User is immediately active

STAKE REFRESH:
  1. Before composing a note, client requests fresh stake from Registry
  2. Stake stored in memory only (not persisted) — fetched fresh each time
  3. This maximises freshness score (minimises delta_t)
```

## REGISTRY

### Core Stack
```
Language:       Python 3.11+
Framework:      FastAPI
Database:       PostgreSQL 15+
ORM:            None. Use raw SQL via psycopg3 (asyncpg also acceptable).
                Schema is tiny. ORM adds unnecessary complexity.
JWT library:    PyJWT with cryptography backend
                pip install pyjwt[cryptography]
                Used for issuing RS256 signed stake JWTs.
Key format:     RSA 2048-bit minimum, 4096-bit recommended
                Registry holds its own RSA keypair for signing stakes.
                Registry public key is baked into client at build time.
```

### PostgreSQL Schema
```sql
-- PUBLIC TABLE: exposed via API (excluding email_hash)
CREATE TABLE key_registry (
  fingerprint    TEXT PRIMARY KEY,         -- sha256 of public key
  public_key     TEXT NOT NULL,            -- RSA public key PEM
  user_tag       TEXT NOT NULL UNIQUE,     -- @handle, unique per registry
  display_name   TEXT,                     -- nullable, optional
  registered_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- PRIVATE TABLE: NEVER exposed via any API response, ever
CREATE TABLE recovery_hints (
  fingerprint    TEXT PRIMARY KEY REFERENCES key_registry(fingerprint) ON DELETE CASCADE,
  email_hash     TEXT NOT NULL             -- sha256 of user-provided email
);

-- TEMPORARY TABLE: nonces for challenge-response flows
CREATE TABLE nonces (
  nonce          TEXT PRIMARY KEY,         -- uuid generated by registry
  fingerprint    TEXT NOT NULL,            -- which key this challenge is for
  expires_at     TIMESTAMPTZ NOT NULL      -- now() + 60 seconds
);
-- Purge expired nonces on read. Optionally add a periodic cleanup job.
```

### FastAPI Route Structure
```
POST   /challenge                  Issue a nonce challenge (requires fingerprint)
POST   /register                   Register new keypair and user_tag
POST   /stake                      Issue a signed stake JWT
GET    /key/{fingerprint}          Public key lookup
GET    /handle/{user_tag}          Handle availability check (404=available, 200=taken)
GET    /registry/public-key        Returns registry's own public key (PEM)
                                   Clients use this to verify stakes.
                                   This is the one route with NO auth.
POST   /rotate/challenge           Issue two nonces for key rotation
POST   /rotate                     Complete key rotation
POST   /revoke                     Revoke key (path A — key intact)
POST   /revoke/email-init          Begin email revocation (path B — key compromised)
POST   /revoke/email-confirm       Complete email revocation with OTP token
```

### Registry RSA Keypair Management
```
Registry has its own RSA keypair stored as environment variables or secrets.
REGISTRY_PRIVATE_KEY_PEM  — used to sign stakes
REGISTRY_PUBLIC_KEY_PEM   — exposed via GET /registry/public-key
                          — baked into client builds as an environment variable

Never store registry private key in the database.
Never log registry private key.
Rotate registry keypair by:
  1. Publishing new public key at /registry/public-key
  2. Clients that re-fetch will pick it up
  3. Old stakes remain verifiable against old public key
     (clients should cache known registry public keys, not just the latest)
```

## BROKER

### Recommended: Go

```
Language:       Go 1.21+
WebSocket lib:  nhooyr.io/websocket (preferred over gorilla, actively maintained)
                or gorilla/websocket (widely used, battle tested)
HTTP:           net/http standard library (no framework needed)
Concurrency:    Goroutines + sync.RWMutex for subscription map
Memory:         In-memory only. Nothing written to disk. Nothing written to DB.
Binary:         Compiles to single static binary. Easy to deploy anywhere.
```

### Go Broker Internal Structure
```
CONNECTION MANAGER:
  map[connectionID] → Connection struct {
    send     chan []byte
    channels map[string]bool
  }
  Protected by sync.RWMutex

ON CLIENT CONNECT:
  Assign connection ID
  Start read goroutine (receives UNTs and commands from client)
  Start write goroutine (sends relayed UNTs to client)

ON RECEIVE (read goroutine):
  Parse UNT (do NOT fully verify — see note below)
  Check type field:
    "note"           → look up channel, fan out to subscribers
    "server_command" → handle command (subscribe/unsubscribe/request_notes/etc.)

ON DISCONNECT:
  Remove from connection map
  Clean up goroutines
  All subscription state for that connection is gone
```

### Note On Broker Verification
```
Broker SHOULD verify UNTs before relaying to avoid wasting bandwidth on garbage.
Broker verification requires knowing the registry public key.
Broker fetches registry public key from GET /registry/public-key on startup.
Broker caches it in memory.

Broker verification steps:
  1. Decode outer JWT
  2. Verify inner stake JWT against cached registry public key
  3. Extract author public key from stake
  4. Verify outer JWT against author public key
  If any step fails: drop silently. Do not relay.

Broker does NOT need to check jti seen-list (that is the client's responsibility).
Broker does NOT need to compute freshness score (that is the client's responsibility).
```

### Alternative: Rust
```
Language:       Rust (edition 2021)
Async runtime:  Tokio
WebSocket:      tokio-tungstenite
HTTP:           axum or warp
Use if:         You need absolute minimum memory footprint
                or have Rust expertise on the team.
Tradeoff:       Significantly longer development time than Go.
                Performance difference vs Go is marginal for this use case.
```

### Alternative: Node.js (acceptable for early prototype only)
```
Runtime:        Node.js 20+ (LTS)
WebSocket:      ws library
Framework:      Fastify (lighter than Express)
Tradeoff:       Higher memory usage than Go or Rust.
                Acceptable for low connection counts (<1000 concurrent).
                Not recommended for production at scale.
```

## CRYPTOGRAPHY REFERENCE

### Algorithms
```
RSA key size:           2048-bit minimum. 4096-bit recommended for new keys.
JWT signing algorithm:  RS256 (RSASSA-PKCS1-v1_5 with SHA-256)
Fingerprint algorithm:  SHA-256 of DER-encoded public key, hex encoded
Email hash algorithm:   SHA-256 of lowercase trimmed email address, hex encoded
Nonce format:           UUID v4, generated by Registry
JTI format:             UUID v4, generated by client
```

### Web Crypto API — Key Operations Reference (Client)
```typescript
// Generate keypair
const keypair = await crypto.subtle.generateKey(
  { name: "RSASSA-PKCS1-v1_5", modulusLength: 4096,
    publicExponent: new Uint8Array([1, 0, 1]), hash: "SHA-256" },
  false,        // non-extractable private key
  ["sign", "verify"]
)

// Export public key as PEM (to send to Registry)
const exported = await crypto.subtle.exportKey("spki", keypair.publicKey)
// base64 encode exported ArrayBuffer → wrap in -----BEGIN PUBLIC KEY----- header

// Sign JWT message (header.payload)
const signature = await crypto.subtle.sign(
  { name: "RSASSA-PKCS1-v1_5" },
  keypair.privateKey,   // CryptoKey from IndexedDB — bytes never exposed
  new TextEncoder().encode(headerDotPayload)
)

// Verify a signature (for received UNTs)
const valid = await crypto.subtle.verify(
  { name: "RSASSA-PKCS1-v1_5" },
  authorPublicKey,      // CryptoKey imported from stake's public_key field
  signature,
  new TextEncoder().encode(headerDotPayload)
)
```

## DEVELOPMENT ORDER RECOMMENDATION

```
1. Registry first
   Get /register, /challenge, /stake, /key/{fingerprint} working.
   Test with curl. Verify RS256 stake JWTs are well-formed.

2. Client crypto layer second
   Key generation, IndexedDB storage, manual JWT construction, UNT assembly.
   Test by verifying produced UNTs against registry public key independently.

3. Broker third
   WebSocket server, subscription map, UNT verification, fan-out.
   Test with two browser tabs.

4. Client UI fourth
   Once crypto layer works, build the glassmorphic React UI on top.

5. Key rotation and revocation last
   These are critical but less frequently used. Build and test after core flow works.

6. Bootstrap server last (future scope)
   After everything else is stable.
```
